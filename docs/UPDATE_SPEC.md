# ТЗ: кнопка «Проверить обновления»

Документ описывает задачу, а не готовый код: на момент написания кнопка нигде
не реализована. Здесь зафиксировано, как она должна работать одинаково во всех
трёх клиентах — веб-панели на VPS, программе для Windows/Linux и приложении
для Android, — чтобы потом не придумывать три разных поведения.

## 1. Зачем

Сейчас пользователь узнаёт о новой версии только зайдя на GitHub. Нужна одна
кнопка, которая скажет: «установлена v1.1.9, доступна v1.2.0» и даст ссылку
(или, где это возможно, скачает файл). Автообновления в задаче нет: программа
работает с сетью и ключами, поэтому решение «ставить или нет» остаётся за
человеком.

## 2. Источник данных

Единственный источник — публичный GitHub Releases API репозитория:

```
GET https://api.github.com/repos/vitazgio/ssh_tunel/releases/latest
Accept: application/vnd.github+json
User-Agent: ssh_tunnel/<версия> (<платформа>)
```

Из ответа берутся четыре поля: `tag_name` (например `v1.2.0`), `name`,
`html_url` (ссылка на страницу релиза) и `assets[]` (имя и `browser_download_url`
каждого файла сборки).

Требования к запросу:

* таймаут 10 секунд, ровно одна попытка — это ручное действие, повторит человек;
* без токена (анонимный лимит GitHub — 60 запросов в час на IP; ошибка 403 с
  заголовком `X-RateLimit-Remaining: 0` показывается как «GitHub временно
  ограничил запросы, попробуйте позже», а не как «обновлений нет»);
* черновики (`draft`) и предрелизы (`prerelease`) игнорируются — эндпоинт
  `/latest` их и так не отдаёт, но если перейдём на `/releases`, фильтр нужен;
* никаких данных о пользователе наружу не уходит: ни адрес сервера, ни имена
  клиентов, ни статистика. В запросе только версия и платформа в User-Agent.

**Про панель на VPS отдельно.** Панель может стоять в сети без выхода наружу.
Ошибку соединения она обязана показывать как «не удалось связаться с GitHub»,
а не как «у вас последняя версия».

## 3. Сравнение версий

Версия и в теге, и в сборке — семантическая: `MAJOR.MINOR.PATCH` с
необязательной буквой `v` впереди. Сравнение — покомпонентно как числа
(`1.10.0` новее `1.9.0`; строковое сравнение здесь дало бы обратное — это
классическая ошибка, поэтому в тестах должен быть именно такой случай).

Результаты сравнения и что показываем:

| Условие | Текст |
|---|---|
| тег новее установленной | «Доступна версия X.Y.Z» + кнопка/ссылка на страницу релиза |
| тег равен установленной | «У вас последняя версия» |
| тег старше установленной (сборка из исходников) | «У вас версия новее опубликованной» |
| версия установленной неизвестна (`dev`, сборка не из тега) | «Не могу определить установленную версию» и всё равно показать последний тег |

Версия установленной сборки уже пробрасывается линкером (`-X main.version`),
отдельного механизма заводить не нужно.

## 4. Что делает каждый клиент

Общее для всех: кнопка не блокирует интерфейс, на время запроса показывает
«Проверяю…» и сама себя выключает, чтобы не начать пять проверок подряд.

### 4.1 Веб-панель (`internal/panel`)

* Кнопка «Проверить обновления» во вкладке «Настройки», рядом с версией.
* Запрос делает **сервер**, а не браузер: `POST /api/update/check` → JSON
  `{"installed":"1.1.9","latest":"1.2.0","newer":true,"url":"https://…","error":""}`.
  Так проверка работает и когда браузер открыт в закрытом контуре, и не упирается
  в CORS.
* Ручка требует входа в панель (как и все остальные `/api/*`).
* Скачивания и установки нет: сервер администрируют через SSH, панель только
  сообщает и даёт ссылку. Ниже — строка вида
  `curl -fsSL … | sudo bash` из docs/PANEL_SETUP.md, чтобы обновить руками.
* Кеш ответа на 1 час в памяти процесса: 60 запросов в час — общий лимит на IP,
  а панель может открывать несколько человек.

### 4.2 Windows/Linux (`internal/webui` + `cmd/ssh_tunnel*`)

* Кнопка в «Настройках», под номером версии.
* Запрос тоже делает Go-часть, ручка `POST /api/update/check`, формат ответа
  такой же, как у панели.
* Если новая версия есть, показываем название файла для этой ОС из `assets[]`
  (`ssh_tunnel_windows_amd64.exe`, `ssh_tunnel_linux_amd64`) и кнопку
  «Открыть страницу релиза» — открывает браузер системным способом.
* Автоматической замены исполняемого файла в этой задаче нет: на Windows
  программа не может переписать саму себя во время работы, а на Linux она обычно
  лежит в `/usr/local/bin` и требует root. Оба случая — отдельная задача,
  которую нельзя делать «заодно».

### 4.3 Android (`android/`)

* Кнопка «Проверить обновления» в общих настройках приложения.
* Запрос делает Kotlin-часть (`HttpURLConnection` в фоновом потоке), не Go-ядро:
  ядру не нужен доступ в интернет мимо туннеля.
* Установленная версия — `BuildConfig.VERSION_NAME`.
* Если версия новее, кнопка меняется на «Скачать APK» и открывает
  `browser_download_url` нужного `.apk` во внешнем браузере. Скачивать внутрь
  приложения и вызывать установщик — не в этой задаче: это требует
  `REQUEST_INSTALL_PACKAGES` и отдельного разговора с Google Play.
* Если Play-версия — кнопку скрыть: магазин обновляет сам, две системы
  обновления одновременно путают.

## 5. Тексты (оба языка)

Все строки идут через существующие словари `i18n` (`ru`/`en`), новых механизмов
локализации не заводить. Ключи:
`update_check` («Проверить обновления» / «Check for updates»),
`update_checking`, `update_latest`, `update_available`, `update_ahead`,
`update_unknown`, `update_failed`, `update_open_release`, `update_download`.

## 6. Что должно быть покрыто тестами

1. Сравнение версий: `1.10.0` > `1.9.0`, `v1.2.0` == `1.2.0`, пустая/`dev`
   версия не роняет функцию.
2. Разбор ответа GitHub из сохранённого JSON-файла (не из сети).
3. Поведение при сетевой ошибке и при 403 rate limit — разные тексты, ни один
   из них не «у вас последняя версия».
4. Кеш: два вызова подряд → один HTTP-запрос.

Сеть в тестах не трогаем: HTTP-клиент передаётся параметром и подменяется
`httptest.Server`.

## 7. Чего в задаче нет

* автоматической установки обновлений;
* фоновой проверки по расписанию и уведомлений;
* канала бета-версий;
* отправки чего-либо о пользователе на сервер.
