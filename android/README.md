# Версия для Android — что уже готово и что осталось

Приложения для телефона пока нет, но **самая рискованная часть уже написана и
проверена**: слой, который превращает сетевые пакеты обратно в соединения.
Здесь описано, как всё устроено и что предстоит.

## Почему нельзя просто пересобрать то же самое

Версии для Windows и Linux работают как **локальный прокси**: они поднимают
SOCKS и HTTP на `127.0.0.1`, а система направляет туда трафик приложений.
В Android такого способа нет:

- общесистемной настройки прокси, которую можно поменять из приложения, там
  не существует — прокси в настройках Wi-Fi действует только на текущую сеть
  и только на часть приложений;
- переменные среды на Android никто не читает;
- единственный настоящий способ увести трафик — `VpnService`, то есть
  виртуальный сетевой интерфейс.

Система отдаёт приложению файловый дескриптор, в который сыплются **сырые
IP-пакеты**. Значит, нужен свой стек TCP/IP в пользовательском пространстве.
Это и есть та часть, которой не было.

## Как устроено

```
приложения телефона
      │  система заворачивает трафик по своим правилам
      ▼
  VpnService  →  tun (файловый дескриптор)
      │
      ▼
  сетевой стек gVisor        ← android/core, новый слой
      │  из пакетов собраны соединения: адрес и порт известны
      ▼
  tunnel.ServeConn           ← ядро из src/, оно же на Windows
      │  SSH direct-tcpip
      ▼
  твой сервер → интернет
```

Ядро туннеля переиспользуется целиком: пул SSH-соединений, keepalive,
переподключение, проверка ключа сервера, правила маршрутизации, лог и
счётчики — всё то же самое, что работает на компьютере.

## Что уже сделано и проверено

Пакет `android/core` — сетевой стек поверх дескриптора от `VpnService`.
Проверки идут на **настоящем** tun-устройстве: пакеты формирует ядро Linux,
SSH-сервер поднят по-настоящему, соединение до цели открывает он же.

| Что проверяется | Тест |
|---|---|
| Пакеты превращаются в соединение, данные не бьются | `TestПакетыСтановятсяСоединением` |
| Вся цепочка до SSH-сервера и обратно | `TestЦепочкаЦеликом` |
| 512 КБ проходят байт в байт | `TestБольшойОтвет` |
| Список «всегда напрямую» действует и здесь | `TestСписокНапрямую` |
| UDP отбивается сразу, а не по таймауту | `TestUDPОтбрасываетсяБыстро` |

```bash
cd android/core
go test ./... -race
```

Тестам нужны `/dev/net/tun` и право создавать интерфейсы; без них проверки,
которым нужно устройство, пропускаются, а не падают.

## Принятые решения

**Отдельный модуль.** Сетевой стек тянет gvisor и требует Go 1.26, а настольной
версии это не нужно — она остаётся на Go 1.22 и трёх зависимостях. Путь модуля
начинается с `sshtunnel/`, поэтому пакеты `internal/` основного модуля остаются
доступными: правило внутренних пакетов смотрит на путь импорта.

**UDP не проходит и не будет.** SSH переносит только TCP — это свойство
протокола. Важно не молчать: если просто выбрасывать пакеты, отправитель ждёт
до таймаута, и браузер вместо быстрого отката с QUIC на TCP выдаёт ошибку.
Стек отвечает «порт недоступен», и клиент переключается за доли миллисекунды —
это измерено в тесте. Приложениям, которым UDP нужен по-настоящему (звонки,
игры), место в списке исключений: там их трафик пойдёт мимо туннеля целиком.

**Отбор приложений делает система.** `VpnService.Builder` умеет
`addAllowedApplication` и `addDisallowedApplication` — те же три режима, что в
настройках на компьютере, только следит за ними Android. Поэтому определять
процесс по сокету (`internal/procinfo`) на телефоне не нужно вовсе, а правила
по программам к трафику из tun не применяются: он уже отобран. Правила по
адресам — «локальная сеть напрямую» и «всегда напрямую» — работают как обычно.

**Локальная сеть не заводится в маршруты.** На Android 13+ есть
`excludeRoute()`, и домашние подсети просто не попадают в туннель — на уровне
ядра, без единой проверки в коде.

## Что осталось

1. **Слой DNS.** Запросы приходят по UDP, а нести их через SSH нечем. План:
   отдавать выдуманный адрес из `198.18.0.0/15`, запоминать пару имя-адрес, и
   когда придёт соединение на этот адрес — передавать наверх **имя**. Тогда его
   разрешит сервер, как и на компьютере, а наружу не уйдёт ни одного запроса.
2. **Приложение на Kotlin**: экран, кнопка, настройки, `VpnService`, выбор
   приложений из установленных.
3. **`protect()` на сокете SSH.** Без него соединение до сервера пойдёт через
   тот же туннель и зациклится. Проверяется только на устройстве.
4. **Сборка APK.** На серверах GitHub есть и SDK, и NDK — там же и подпись.

## Что делать на телефоне сейчас

Пока приложения нет, остаются готовые клиенты, которые умеют SSH и SOCKS:
**ConnectBot** (проброс порта по SSH) вместе с браузером, поддерживающим
SOCKS-прокси, или **Termux** с обычным `ssh -D 1080`. Не так удобно, но через
тот же сервер и тот же ключ.
